# BookmarksTab Postgres transitions — tech design

## Product spec and intent

- **Product spec:** `brain/tasks/specs/done/bookmark-analytics-postgres.md`
- **Related shipped design:** `docs/specs/bookmark-pipeline-analytics-postgres-transition-log-tech-design.md`
- **Task:** `5c87ea16-bc06-4069-bed1-73f2916b48a2` — 💻 Wire BookmarksTab transitions to Postgres analytics schema

The analytics spec requires the dashboard to use the Postgres transition log and the original analytics design states that consumers should query `analytics.bookmark_transitions` directly rather than add a REST service. This task completes that read-side cutover while retaining the JSONL log as a degraded local fallback. The state snapshot remains file-backed.

## `.openclaw` boundary

No `.openclaw` configuration, extension, agent definition, or scheduler change is required. `DATABASE_URL` is runtime configuration supplied by the existing local development environment; this change must not add credentials to the repository. The fallback reads workspace-owned `brain/state/bookmark-transitions.jsonl` through the existing `WORKSPACE_ROOT` resolution, and no brain file is modified.

## Ownership boundary check

- **Natural source of truth:** database-backed bookmark analytics data in `analytics.bookmark_transitions`. The JSONL file remains the workflow's authoritative append-only operational trail, but Postgres is the queryable analytics read model already written by the bookmark workflow.
- **Owning boundary:** the analytics schema remains outside the Tasks API domain, as documented by its migration. Mission Control's dev-only Vite middleware is the direct local analytics consumer; no route is added to `services/tasks-api`.
- **Direct consumers:** `apps/mission-control/src/bookmarkStateSource.js` calls the Vite middleware's `/api/transitions` endpoint; `BookmarksTab` consumes the unchanged transition-event shape.
- **Why direct SQL:** the product intent explicitly prefers direct analytics queries and the Vite plugin is already a local-only adapter. Creating a service for this one read would add an unnecessary boundary.
- **Incremental posture:** this is a small durable cut: replace only the transition source. `/api/state` remains file-backed because bookmark state has not migrated to Postgres. The JSONL fallback prevents local development from depending on database availability.
- **Temporary placement:** the Vite middleware is intentionally dev-only. If Mission Control later needs this data in a deployed build, that is a separate analytics-service design; this task must not turn Vite middleware into a production API.

## Implementation plan and file scope

   - Add `pg` to `apps/mission-control/package.json` as a runtime dependency because `vite.config.js` imports it while running the development server.
   - Update the repository lockfiles generated by the package manager; do not rely on a transitive `pg-*` package.
2. **Make the transitions loader explicit and testable in `apps/mission-control/vite.config.js`.**
   - Keep `resolveBrainRoot()` and the existing JSONL parser as the fallback path.
   - Create one lazily initialized `pg` client/pool for the dev server when `DATABASE_URL` is non-empty; avoid opening a connection at config-import time.
   - Query `analytics.bookmark_transitions` ordered by `occurred_at ASC, id ASC` so the response preserves JSONL chronology.
   - Normalize each row to the existing event contract:
     - `key` ← `bookmark_key`
     - `from` ← `from_status`
     - `to` ← `to_status`
     - `at` ← `payload.at`, falling back to `occurred_at` serialized as ISO-8601

     - `reason` ← `payload.reason`, falling back to an empty string

   - Verify `/api/state` remains file-backed and does not issue a database query.

## Data model and API contract changes

### Database

No migration or write-path change is required. The implementation reads the existing columns:

`id`, `occurred_at`, `bookmark_key`, `from_status`, `to_status`, `actor`, and `payload` from `analytics.bookmark_transitions`.

The query is read-only and parameter-free. Existing indexes support time ordering and future filtering. The table continues to be populated best-effort by `agents/workflows/bookmarks/scripts/analytics_db.py`.

### HTTP response

`GET /api/transitions` remains a dev-only, same-origin endpoint returning a JSON array. Its public response shape is intentionally unchanged:

```json
{
  "key": "bookmark-key",
  "from": "summarized",
  "to": "spec_requested",
  "at": "2026-08-15T00:00:00.000Z",
  "actor": "lobster_generate_specs.py",
  "reason": "high-signal curation"
}
```

No client change is expected in `bookmarkStateSource.js` or `BookmarksTab.jsx`. Database-only fields (`id`, `source`, and the full `payload`) are not exposed. `/api/state` continues to return `bookmark-review-state.json` unchanged.

## Workflow, cron, and skill changes

- **Bookmark workflow:** no mutation/write behavior changes; Postgres mirroring remains best-effort after JSONL append.
- **Cron/lobster:** no changes.
- **Skills/agents:** no changes.
- **Runtime:** local Mission Control uses `DATABASE_URL` when present. Database absence or failure degrades to JSONL without making the tab unavailable.

## Open questions and risks

1. **Historical payload completeness:** rows created by the current writer include `payload.at` and `payload.reason`; older or manually inserted rows may not. The normalizer must fall back to `occurred_at` and `""` rather than discard the row.
2. **Connection lifecycle:** a pool must be lazy and closed on server shutdown. Creating a client at module import would make builds/tests unexpectedly attempt database access.
3. **Duplicate history:** fallback is all-or-nothing per request. Do not merge DB and JSONL rows, which would require deduplication and could double-count transitions.
4. **Database lag:** because mirroring is best-effort, a reachable database may contain fewer rows than JSONL. This task follows the product decision that Postgres is the analytics read model; it does not reconcile or backfill missing rows.
5. **Production exposure:** the Vite endpoint remains dev-only. A deployed Mission Control read path requires a separately owned analytics API and authentication review.
