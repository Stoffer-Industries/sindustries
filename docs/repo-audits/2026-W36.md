# Sindustries Repository Audit — 2026-W36

## Executive Summary

**Health grade: B.** This was a consolidation week: the repo cleaned up three of
last week's blockers rather than shipping new surfaces. **W35 ledger:** the
vestigial `pnpm-lock.yaml` is deleted (single npm `package-lock.json` remains);
the extracted `content-scheduler-api` now has a real CI job
(`.github/workflows/ci.yml:230`, vitest + Prisma migrate); and the Fly deploy
Dockerfiles were switched to `npm ci` (`666977b`). Good direction on all three.
**The one W35 finding still open is the security one:** `content-scheduler-api`
mounts every write route (`create/patch/approve/unapprove/remove/reorder`) with
**no authentication middleware** — the `requireAuthenticatedUser` gate the code
comments and a `.skip`ed test both reference ("audit 2026-W35 T1.2", task
`0719a8e3`) was never wired into `createApp` (`src/app.ts:63-110`). Because no
middleware populates `req.user`, the `actor()` helper falls through to the
attacker-controlled `x-actor` header (`src/routes/contentScheduler.ts:58-77`), so
`approvedBy` is spoofable and approvals are unauthenticated. **Severity is
High-latent, not live-Critical:** the HTTP `createApp` is not yet Fly-exposed —
only the headless BullMQ worker is deployed (`auto-post-worker.fly.toml`, no
`[http_service]`) — so today the surface is localhost/prodlike only. It becomes
Critical the moment the write API gets its own Fly app. The other new finding is a
**fail-open in the feature-task merge gate**: `clippy_evidence_failures` skips the
Rust clippy-evidence check whenever `pr_changed_files` returns empty, and that
function swallows *every* `gh` error into an empty Vec
(`src/main.rs:4518-4544`, `4595-4597`) — so a transient `gh`/API blip lets a Rust
feature-task PR clear the gate with no clippy evidence, while the sibling
`pr_body` read in the same function fails *closed*. Top risks: (1) latent
unauthenticated scheduler writes, (2) clippy-gate fail-open on gh failure, (3)
`feature-task/src/main.rs` has grown to **8,658 lines / 205 top-level items** — a
god file. Top opportunities: land the T1.2 auth middleware before HTTP exposure;
make `pr_changed_files` failures fail the gate closed; carve production `main.rs`
into modules (the pattern already exists — `ac_parsing.rs`, `analytics.rs`). No
verified live Critical this week.

workflows — Tasks, Mission Control, GymTrack, Budget, Website, shared UI/design
tokens, backend APIs, and Rust/Python automation.

the Fly deploy topology (three `*.fly.toml`, three Dockerfiles, three
`deploy-staging-*.yml` workflows).

**Key directories:** `apps/` user products (tasks, mission-control, gymtrack,
budget-mobile, website); `services/` four backend domains; `packages/` shared libs

Fly/Docker deploy artefacts; `.github/workflows/` CI + per-service deploys;
`docs/` architecture, specs, runbooks, audits.

## Audit Report

### Strengths

- **W35 blockers were actually closed, not papered over.** The pnpm lockfile is
  deleted, `content-scheduler-api` has a genuine CI job that runs vitest against a
  migrated Postgres (`ci.yml:230-286`), and the Fly Dockerfiles moved to `npm ci`.
  This is the healthy pattern: audit finding → fix → next audit verifies.
- **The feature-task test-outcome matching is defensively written.**
  `cargo_test_leaf_outcome` (`src/main.rs:4278`) explicitly refuses to trust
  cargo's process exit code (0 both for "passed" and "matched zero tests") and
  returns failure when no cited test ran — the documented no-silent-pass
  discipline. `resolve_repo_file_by_name` similarly errors on ambiguous filename
  matches instead of guessing.
- **The auto-post worker deploy is correctly modeled as a non-HTTP process.**
  `auto-post-worker.fly.toml` has no `[http_service]`/`http_checks`, relies on Fly
  process supervision, and pins BullMQ as the durable adapter — the right shape for
  a queue consumer, and it keeps the unauthenticated write API off the internet.
- **CI coverage now spans every long-lived subsystem.** `ci.yml` runs jobs for
  otel-node, mission-control, tasks-api (unit + DB integration), content-scheduler-api,
  the Rust feature-task workflow, ash, and the Python workflows — the "new service
  ships with zero CI" pattern flagged in W33–W35 did not recur this week.

### Security

- **A1 — `content-scheduler-api` write endpoints are unauthenticated; audit trail
  is spoofable (High-latent, fact). Carryover of W35 finding #2 — still open.**
  ➡️ Tracked by task bd755ad4 (bd755ad4-314e-410d-84ec-0083178a7ea2).
  `createApp` (`services/content-scheduler-api/src/app.ts:63-110`) mounts
  `contentSchedulerRouter` with helmet, CORS, JSON parsing, and a rate limit on
  `publish` only — **no auth middleware**. The write routes
  (`POST /content-scheduler/items`, `PATCH …/:id`, `…/approve`, `…/unapprove`,
  `…/remove`, `POST …/reorder`; `src/routes/contentScheduler.ts:151-664`) have no
  per-route guard either. The `actor()` helper reads `req.user?.actor`
  (`:64`), but nothing populates `req.user`, so it falls through to the
  client-supplied `x-actor` header — meaning `approvedBy` on an approval is
  attacker-chosen. The code comment (`:59`) and a `.skip`ed test
  (`test/contentScheduler.test.ts:437`, "gated on audit 2026-W35 T1.2
  requireAuthenticatedUser", task `0719a8e3`) both confirm the middleware was
  planned and never landed. Only `publish` (`x-actor-secret`) and
  `imports/cto-craft` (`x-content-ingest-secret`) are guarded. **Why latent, not
  live-Critical:** the HTTP app is not deployed to Fly — only the headless worker
  is (`infra/cloud/fly/auto-post-worker.fly.toml`) — so exposure today is
  localhost/prodlike. It becomes Critical the instant a `content-scheduler-api`
  Fly app with an `[http_service]` is added. Classification: `tracked-code-task`
  (already gated as "W35 T1.2"; see Open Questions on whether a Tasks-API task
  exists).

### Code quality / correctness

- **A2 — feature-task clippy-evidence gate fails open on transient `gh` failure
  (Medium, fact).**
  ➡️ Tracked by task afe39f3d (afe39f3d-b6c8-4d40-a264-e88dbcf66d6c).
  `clippy_evidence_failures` (`src/main.rs:4591-4605`) calls
  `pr_changed_files(url)` and, if `touches_rust_feature_workflow(files)` is false,
  returns "no failures" — i.e. the Rust clippy-evidence requirement is skipped.
  But `pr_changed_files` (`:4518-4544`) returns an **empty Vec on any `gh`
  error** ("Returns an empty Vec if … the `gh` call fails"). So a transient
  `gh pr view --json files` failure makes `is_rust_pr`/`touches_rust_*` false and
  a Rust feature-task PR clears the clippy gate with zero evidence. The
  inconsistency is stark: the very next line reads the PR body and treats a
  `pr_body` error as a **failure** (fail-closed, `:4602-4604`), while the file-list
  error fails **open**. The same empty-on-error value also drives the
  `DispatchingTestRunner { is_rust_pr }` disambiguator (`:889-890`), so a gh blip
  can also misroute bare Rust test citations. Consequence: a mechanical merge gate
  that is supposed to be non-bypassable can be bypassed by an infrastructure blip.
  Classification: `tracked-code-task`.

- **A4 — `cargo_test_leaf_outcome` matches on leaf name only; cross-module leaf
  collisions can yield a false pass (Low, judgment).**
  ➡️ Folded into A3 task d578e547 (d578e547-e0ab-413d-abbb-3fd1a0098921).

  The matcher
  (`src/main.rs:4288-4292`) compares only the post-`::` leaf segment of each cited
  test. If two modules both define e.g. `tests::works`, a cited `works` is
  satisfied by whichever passes — and if the *intended* test does not exist but a
  same-named test elsewhere passes, the AC is marked satisfied. This contradicts
  the ambiguity-error discipline `resolve_repo_file_by_name` applies for shell
  tests (which errors on >1 match). Low severity because same-leaf collisions are
  rare in this crate today and the conservative "any match fails ⇒ fail" rule
  limits blast radius, but it is a latent evidence-integrity gap. Classification:
  `tracked-code-task` (small) or fold into A3's refactor.

## Improvement Strategy

Three themes explain this week's findings:

1. **Auth must travel with an extracted service before it is exposed (A1).**
   Target state: `content-scheduler-api` mounts `requireAuthenticatedUser` on all
   write routes and populates `req.user` so `actor()` uses an authenticated
   identity, before any `[http_service]` Fly app for it exists. Principle: a
   service's security posture is part of its contract, not a follow-up; extraction
   PRs must carry the guard, not defer it to a "Phase 2" that slips across weeks.
   Done = the `.skip`ed test at `contentScheduler.test.ts:437` is un-skipped and
   green, and no write route is reachable without an authenticated actor.

2. **Mechanical merge gates must fail closed (A2, A4).** Target state: gate helpers
   distinguish "the check ran and passed" from "the check could not run." Principle:
   an evidence gate that can't fetch its evidence should block, not wave the PR
   through. Done = `pr_changed_files` surfaces gh errors to callers (Result, or a
   distinct sentinel) and `clippy_evidence_failures` treats an unknown file list as
   a failure; test-name matching is unambiguous or errors on ambiguity.

3. **Split the lobster god file (A3).** Target state: `main.rs` retains only CLI
   entry/dispatch; TestRunners, PR-gate helpers, staging, and cleanup move to
   sibling modules alongside `ac_parsing.rs`/`analytics.rs`. Principle: the factory's
   most critical binary should be as reviewable as the code it gates. Done = no
   single file over ~2k lines and each concern in a named module with its own tests.

**Explicitly NOT recommending:** deploying a `content-scheduler-api` HTTP Fly app
this week (it would convert A1 from latent to live); a big-bang rewrite of `main.rs`
(mechanical module extraction only, behavior-preserving); loosening code-garden to
absorb A1/A2 (both are behavior-sensitive and belong in tracked code tasks).
