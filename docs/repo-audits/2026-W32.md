## Executive Summary

**Health grade: B.** Sindustries is a well-documented early-production monorepo with clear app/service/package boundaries, active CI, and strong recent work on structured task approvals and workflow validation. The principal risks are operational: tasks-api workflow-mutating endpoints lack an application authentication boundary, the approval migration performs broad writes and destructive rollback through HTTP with limited guardrails, and the feature-task workflow remains a 7,120-line Rust entrypoint. Recent improvements are meaningful: CI runs the bookmark Python suites, budget-api uses sessions and encrypted token storage, and approval behavior has dedicated tests. No Critical issue was verified, but the unauthenticated write surface is High until loopback-only operation is enforced or authentication is added.

## Repo Map

**Purpose:** Monorepo for Sindustries product surfaces and agent-operated workflows: Tasks, Mission Control, GymTrack, Budget, Website, shared UI/design tokens, backend APIs, and Rust/Python automation.

**Stack:** Node.js 22; npm workspaces (`package.json:2-17`); React/Vite web apps; Expo mobile app; Express + Prisma + PostgreSQL services; Supabase for GymTrack; Rust feature-task workflow; Python operational workflows; Docker Compose/Tilt; GitHub Actions.

**Architecture:** `apps/*` clients call domain services (`services/tasks-api`, `services/budget-api`) and Supabase; `packages/*` contains shared UI, tokens, telemetry, and domain code; `infra/*` owns runtime wiring; `agents/*` owns automation.

**Key directories:** `apps/` user-facing products; `services/` backend domains; `packages/` shared libraries; `agents/workflows/feature-task/` Rust Lobster workflow; `agents/workflows/bookmarks/` Python bookmark pipeline; `docs/` architecture, system references, specs, runbooks, and audits; `.github/workflows/` CI/deploy.

**Surprise:** The approval change has unusually good focused tests, while its migration remains a thin HTTP client and inherits the API's trust model.

## Audit Report

### Strengths

- Clear boundaries and ownership rules in `README.md:3-17` and `docs/ARCHITECTURE.md`.
- CI covers all four Python workflow test locations (`.github/workflows/ci.yml:40-60`) plus dedicated API, app, Rust, and package jobs.
- Approval API, migration detection, legacy parsing, and UI have dedicated tests (`services/tasks-api/test/{taskApprovals,requiredApprovals,legacyApprovals}.test.ts`, `apps/tasks/src/components/ApprovalsSection.test.jsx`).
- Budget security improved: session-derived user identity and ownership checks (`services/budget-api/src/routes/transactions.ts:13-18,42-47`) and encrypted token bytes (`services/budget-api/prisma/schema.prisma:42-44`).
- Root documentation covers isolated dev/prodlike stacks and migrations (`README.md:21-111`).

### Architecture & design

**[High] Approval writes have no application authentication boundary.**

- **Where:** `services/tasks-api/src/app.ts:98-105` mounts `taskApprovalsRouter`; `services/tasks-api/src/routes/taskApprovals.ts:60-107,113-148` mutates approvals and trusts caller-supplied `owner` at `:73-75`.
- **Why:** Any caller that can reach the API can create, replace, or revoke the workflow approvals consumed by Lobster, and can choose the recorded owner. The code may be safe under strict loopback-only deployment, but that assumption is not enforced at the HTTP boundary.
- **Severity:** High.

**[Medium] Required-approvals configuration silently falls back after malformed configuration.**

- **Where:** `services/tasks-api/src/config/requiredApprovals.ts:117-141` catches parse/read errors and returns defaults; `services/tasks-api/src/routes/requiredApprovals.ts:31-40` returns a valid response with `source`.
- **Why:** A typo or partial deployment can change policy while the service remains healthy; the warning is easy to miss and callers receive a successful response.
- **Severity:** Medium.

**[Medium] Feature-task workflow remains a 7,120-line Rust entrypoint.**

- **Where:** `agents/workflows/feature-task/src/main.rs:1-80` declares only `mod analytics`; the file is 7,120 lines and contains stage/parsing functions through at least `:3547`.
- **Why:** Loading, approval-source selection, PR inspection, AC parsing, delivery verification, analytics, and post-merge behavior have a large shared regression surface. Extracting stage modules would improve review and focused testing.
- **Severity:** Medium.

### Code quality

**[Medium] Legacy approval migration is non-transactional and per-row.**

- **Where:** `services/tasks-api/scripts/migrate-legacy-approvals.ts:137-181,242-294` fetches all tasks and posts one approval at a time.
- **Why:** A failure after several successful POSTs leaves a partial migration. Retry is idempotent for existing rows, but progress is not checkpointed and the snapshot is written only after the loop.
- **Severity:** Medium.

**[Low] Configuration parser is a permissive bespoke YAML subset.**

- **Where:** `services/tasks-api/src/config/requiredApprovals.ts:57-114` ignores unknown top-level keys and malformed entries.
- **Why:** Typos can be accepted with semantics different from operator intent. A strict schema would make policy changes safer.
- **Severity:** Low.

### Security

**[High] Approval API trusts caller identity and is mounted alongside unauthenticated workflow writes.**

- **Where:** `services/tasks-api/src/app.ts:63-79,98-105` configures CORS and mounts routes but no session, API-key, or internal-secret middleware; `taskApprovals.ts:68-75` accepts arbitrary `owner` input.
- **Why:** CORS is not authentication. Non-browser callers bypass it, and reachable clients can forge approval state and owner identity.
- **Severity:** High.

**[Medium] Migration rollback deletes listed approvals without confirmation or integrity checks.**

- **Where:** `services/tasks-api/scripts/migrate-legacy-approvals.ts:23-29,297-313` reads arbitrary JSON and calls DELETE for each row.
- **Why:** A stale, edited, or wrong-environment snapshot can revoke approvals in bulk; there is no schema version, target identity, or created-by-run check.
- **Severity:** Medium.

### Testing

**[Medium] Migration tests do not cover interrupted write/resume/rollback behavior.**

- **Where:** `services/tasks-api/test/legacyApprovals.test.ts`; orchestration at `migrate-legacy-approvals.ts:242-294`.
- **Why:** Parsing tests do not prove pagination, per-row failure, snapshot creation, retry, and rollback interact safely.
- **Severity:** Medium.

**[Low] Configuration fallback is not an operational CI-visible failure.**

- **Where:** `requiredApprovals.ts:117-141`.
- **Why:** A malformed `.openclaw` file can switch policy to defaults; tests should assert the warning/health behavior and resolved source.
- **Severity:** Low.

### Performance

**[Low] Backfill is chatty at scale.**

- **Where:** `taskApprovals.ts:43-54` does separate task and approval queries; migration posts one request per row (`migrate-legacy-approvals.ts:249-260`).
- **Why:** Current volumes are acceptable, but large backfills add one HTTP round trip per approval; bounded batch or server-side transaction would reduce pressure.
- **Severity:** Low.

### Dependencies

No high-confidence dependency or lockfile defect was identified. Root and relevant workspace lockfiles are committed.

### DevEx & operations

**[Medium] Approval policy depends on mutable host-local configuration.**

- **Where:** `requiredApprovals.ts:39-43`; comments at `:3-6` state the file is read from `$HOME/.openclaw`.
- **Why:** Two environments can run different policies on the same commit. The endpoint reports version/source, but startup/health does not make drift prominent.
- **Severity:** Medium.

**[Low] Main merges publish mobile artifacts directly.**

- **Where:** `.github/workflows/ci.yml:9-38` publishes EAS on every push to main.
- **Why:** This is reasonable at current distribution, but a post-publish health signal and rollback path would reduce future blast radius.
- **Severity:** Low.

### Documentation

**[Low] Migration safety contract exists in source comments but not a durable runbook.** ✅ [PR #376](https://github.com/Stoffer-Industries/sindustries/pull/376)

- **Where:** `migrate-legacy-approvals.ts:18-33`; no approval-migration runbook was present in the inspected `docs/runbooks/` list.
- **Why:** Environment selection, dry-run, snapshot retention, partial failure, and rollback limits should be discoverable without reading source.
- **Severity:** Low.

## Improvement Strategy

### Theme 1 — Explicit internal trust boundary

**Target:** Approval, lifecycle, scheduler, and social-posting writes require sessions or a scoped internal secret, and unsafe non-loopback binding is refused. **Principle:** Network reachability is not authorization. **Trade-off:** A short-term rotated internal secret is acceptable while product identity integration remains separate. **Done:** Unauthorized approval mutations fail; authorized agent/UI flows pass; trust mode is visible in diagnostics.

### Theme 2 — Resumable, auditable migrations

**Target:** Backfill has bounded batches, durable progress, versioned snapshots, target identity, and rollback limited to rows created by that run. **Principle:** A migration is an operational product. **Trade-off:** No general framework is needed, but interruption/recovery must be explicit. **Done:** Injected failure resumes without duplicates and mismatched rollback is rejected.

### Theme 3 — Reduce workflow coupling

**Target:** Feature-task stages are modules with explicit inputs/outputs; approval-source logic is isolated from PR/AC parsing. **Principle:** Orchestration should compose focused validators. **Trade-off:** Extract by stage boundary, not every helper. **Done:** `main.rs` is orchestration-focused and stage tests run independently.

**Quick wins:** internal-secret middleware and negative tests (S–M); expose policy source/hash (S); add snapshot schema/version/base URL/created IDs (S); write an approval migration runbook (S).

**Not recommended now:** replacing the workspace or creating a new service solely for approvals; boundaries and CI are adequate, while trust and operability are the urgent gaps.

## Task Plan

### Milestone 0: Safety net

1. **Instrument approval policy state** — expose resolved path, version, source, and non-secret hash. **Areas:** config, health, docs. **AC:** operators identify active policy; malformed config is visible. **Effort:** S. **Risk:** Low. **Dependencies:** none.
2. **Document and version migration snapshots** — add runbook, schema/version, target API/environment, and created row IDs. **Areas:** runbook and migration script. **AC:** dry-run, verification, and rollback are reproducible and mismatched snapshots reject. **Effort:** M. **Risk:** Low. **Dependencies:** none.

### Milestone 1: Critical fixes

3. **Protect workflow-mutating API routes** — add session/internal-secret auth to approvals and other sensitive writes. **Areas:** app, middleware, routes, callers/tests. **AC:** unauthorized requests fail; owner cannot be forged; authorized flows pass. **Effort:** M. **Risk:** Medium. **Dependencies:** choose auth contract.
4. **Harden migration interruption and rollback** — batch writes, checkpoint progress, and scope rollback to rows created by the run. **Areas:** script, tests, runbook. **AC:** injected failure resumes without duplicates; rollback is scoped. **Effort:** L. **Risk:** Medium. **Dependencies:** tasks 2–3.

### Milestone 2: High-leverage improvements

5. **Extract feature-task stages into Rust modules** — preserve CLI behavior while isolating load, approval, PR, AC, delivery, analytics, and post-merge stages. **Areas:** Rust workflow and tests. **AC:** behavior remains unchanged; stage tests are focused; main is orchestration. **Effort:** XL. **Risk:** Medium. **Dependencies:** none.
6. **Add bounded bulk approval backfill** — replace one-request-per-row with transaction-aware batches. **Areas:** API, script, integration tests. **AC:** batch size and failures are reported; semantics are tested. **Effort:** L. **Risk:** Medium. **Dependencies:** task 4.

### Milestone 3: Quality & polish

7. **Strictly validate approval config** — reject unknown task types, malformed entries, and duplicates. **Areas:** config, tests, docs. **AC:** malformed fixtures fail clearly; partial overrides behave intentionally. **Effort:** M. **Risk:** Low. **Dependencies:** task 1.
8. **Add migration telemetry** — emit counts, duration, failure phase, and policy version without secrets. **Areas:** script, OTel/logging, runbook. **AC:** empty, partial, and successful runs are distinguishable. **Effort:** M. **Risk:** Low. **Dependencies:** task 4.
