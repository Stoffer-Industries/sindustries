## Repo Map

**Purpose:** Monorepo for Sindustries product surfaces and agent-operated
workflows — Tasks, Mission Control, GymTrack, Budget, Website, shared UI/design
tokens, backend APIs, and Rust/Python automation.

**Stack:** Node.js 22; **npm workspaces** (`apps/*`, `packages/*`,
`services/*`); React/Vite web apps, with Mission Control and Tasks hosted as
separate Vercel projects; Expo mobile;
Express + Prisma + PostgreSQL services (`tasks-api`, `budget-api`,
`content-scheduler-api`); BullMQ + Redis for durable auto-post; Supabase + a
standalone OAuth MCP server (`gymtrack-mcp`, plain JS); a Rust feature-task
("lobster") workflow; Python/LangGraph operational workflows; GitHub Actions CI
with a per-service/per-app test job matrix; Fly.io `syd` staging deploys for
APIs and workers.

**Architecture:** `apps/*` clients call domain services; `packages/*` holds
shared UI/tokens/telemetry/domain code (`design-tokens`, `ui`, `otel-node`,
`budget-domain`); each domain owns its own service. `content-scheduler-api` is
split into an auth-gated HTTP `createApp` and a headless BullMQ worker
(`autoPostWorkerMain.ts`, the only piece on Fly). `gymtrack-mcp` is a
self-contained OAuth 2.1 authorization server + MCP JSON-RPC resource server.
`infra/cloud/fly/*` holds **three** service specs (tasks-api, budget-api,
auto-post-worker) with matching Dockerfiles and deploy workflows. Mission
Control and Tasks use co-located `apps/{mission-control,tasks}/vercel.json`
configs instead.

**Key directories:** `apps/` user products; `services/` four backend domains;
`packages/` shared libs; `agents/workflows/feature-task/` the Rust lobster;
`infra/cloud/` backend Fly deploy topology; `docs/{systems,specs,runbooks,repo-audits}/`
durable docs; `scripts/dev/up.sh` the local Colima/Tilt bring-up.

**What surprised me (positive):** CI has a dedicated test job for *every* service
and app — including a `gymtrack-mcp-tests` vitest job that guards the OAuth
refresh-rotation path on every PR (`.github/workflows/ci.yml:531`). Test
discipline here is above what the project's maturity would predict.

## Audit Report

### Security

- **[High] gymtrack-mcp public OAuth endpoints have no rate limiting.** *(Fact.)*
  `/oauth/register` (`src/app.js:347`) is open Dynamic Client Registration
  (`registration_endpoint_auth_methods_supported: ['none']`,
  `src/app.js:342`) — any unauthenticated caller can create an OAuth client row
  via `repo.createDynamicOAuthClient` (`src/app.js:359`) with no throttle.
  `/oauth/token` (`src/app.js:498`) is likewise unthrottled. No rate-limit
  middleware exists anywhere in `services/gymtrack-mcp/` (grep: zero hits),
  whereas the sibling `content-scheduler-api` gates its write endpoints with
  `createRateLimit` (`content-scheduler-api/src/app.ts:98-103`). **Consequence:**
  unbounded client-registration rows (DB growth / storage abuse) and an
  unmetered surface for credential-stuffing the token endpoint. The OAuth logic
  itself is sound (PKCE S256 enforced, single-use codes, hashed tokens, refresh
  replay detection) so this is a hardening gap, not a broken-auth bug — hence
  High, not Critical. `➡️ tracked-code-task` (see Task Plan T1.1). `➡️ Tracked by task 37bbc104 (37bbc104-613e-4266-b5f7-cd7de08b4551)`.

- **[Info / verified-fixed] W36 A1 — content-scheduler unauthenticated writes.**
  Now gated: `methodGate(new Set(['POST','PATCH','DELETE']),
  requireAuthenticatedUser)` on `/items` and `/reorder`
  (`content-scheduler-api/src/app.ts:129-137`); GET surface stays public per the
  auth matrix. Service-to-service router is mounted *before* the gate by design
  (`app.ts:114`). No live exposure regardless (worker-only on Fly). Closed.

- **[Low] `POST /x/tweets` is intentionally unauthenticated but not defended in
  depth.** *(Fact + judgment.)* `xTweetRouter` mounts a real tweet-publishing
  route (`content-scheduler-api/src/routes/xTweet.ts:44`) outside the
  `/items`+`/reorder` auth gate. The file header documents this as a deliberate
  localhost-only, in-cluster contract with an explicit "MUST be locked down
  before external exposure" warning (`xTweet.ts:31-38`). Not exposed on Fly
  today, so Low — but it is a second write surface that a future HTTP exposure of
  `createApp` would silently un-gate. Worth a header-token or LAN-allowlist guard
  when the scheduler HTTP app is first deployed. `needs-human-decision` at
  exposure time (Open Questions).

- **[Info] No hardcoded secrets.** Secret-shaped grep hits across
  `services/`, `apps/`, `packages/` are all test fixtures (fake `*-token-long-enough`
  strings, e.g. `tasks-api/test/mutationAuthIntegration.test.ts:10-13`).
  `.gitleaks.toml` is present. Clean.

## Improvement Strategy

**Theme 1 — Harden public unauthenticated write surfaces.** The gymtrack-mcp
OAuth server and the `POST /x/tweets` route are both correct-but-undefended:
no rate limiting, and (for x/tweets) no auth by design. *Target state:* every
public write endpoint has a rate limit; every "localhost-only" route has a
positive guard (header token or allowlist) so it fails closed if the network
boundary changes. *Principle:* defense in depth — the network perimeter is not
the only line of defense. *Done signal:* a rate-limit middleware wraps
`/oauth/*` in gymtrack-mcp; `POST /x/tweets` rejects requests lacking an
in-cluster token.

**Theme 2 — Platform fit for staging surfaces (resolved).** Commit `577906f`
removed the two frontend Fly app definitions before deployment and moved the
static SPAs to separate Vercel projects. The three remaining Fly workloads are
APIs/workers with matching deploy workflows. *Principle:* choose deployment
automation by workload type rather than forcing static frontends into the
backend runtime. *Done signal:* Vercel configs, staging aliases, smoke tests,
and rollback evidence are recorded in `docs/systems/mission-control.md`.

**Theme 3 — Finish the `main.rs` carve.** Continue extracting cohesive modules
from the lobster's `main.rs`. *Target state:* `main.rs` is orchestration-only,
each concern in a sibling module. *Principle:* a file small enough to review is
a file safe to change. *Done signal:* `main.rs` < ~3k lines. **NOT recommending**
a big-bang rewrite — the incremental extraction already in flight is the right
shape. (Tracked from W36 via task `9b10c65a`; W38+ follow-up via task
`fd1aeef8` to close AC1.)
