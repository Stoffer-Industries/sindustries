# SIndustries repository audit — 2026-W43

## Executive Summary

Overall health: **B-** (engineering judgment): service ownership, layered tests and deployment gates are strong, but gaps between declared contracts and their enforcement remain material.
This audit inspected commit `d51958c8` on 2026-10-19, Pacific/Auckland, using a separate audit worktree; it changed no source code.
The top three risks are an unreachable Content Scheduler automatic deployment condition, a fail-open secret scanner, and malformed JSON being misreported as server faults.
The top three opportunities are producer/consumer checks for CI outputs, consistent HTTP error contracts, and measured query/typechecking budgets.
Six evidence-backed findings are recorded below, with two code tasks and two research tasks created; secret-scanner policy needs a human decision and the documentation clarification is garden-safe.
The staging harness suite passed 12/12 tests and the existing deployment-gate contract suite passed, while an independent reference/export check identified the missing scheduler output.
This is a sampled source/configuration audit, not a penetration test or a full application regression run; live deployment state, database volumes, dependency advisories and license compliance were not verified.

## Repo Map

### Purpose, maturity and stack

SIndustries combines personal/business product apps with an agent-operated delivery platform; it is an actively deployed small-team system, not merely a prototype (`README.md:5`, `README.md:28`). React/Vite web apps coexist with Expo/React Native mobile, Express/TypeScript APIs and Prisma/PostgreSQL persistence. ### Control/data flow and conventions

Browser/mobile requests enter service middleware, then domain routes and Prisma repositories. Budget derives user identity from a session before financial routers (`services/budget-api/src/app.ts:76`); transaction ownership is checked before mutation (`services/budget-api/src/routes/transactions.ts:48`). Tasks exposes read surfaces while gating mutations (`services/tasks-api/src/app.ts:91`). Scheduler jobs reconcile current persisted state before choosing the publish service (`services/content-scheduler-api/src/workers/autoPostWorker.ts:53`). CI computes changed surfaces, aggregates tests in a merge gate and invokes per-service reusable deployment workflows (`.github/workflows/ci.yml:13`, `.github/workflows/ci.yml:1037`, `.github/workflows/ci.yml:1101`).

Existing conventions worth preserving: domain-owned schemas, explicit service boundaries, JSON error responses, injectable/testable workers, Supertest/Vitest tests, real database integration jobs, and spec-first change documentation (`CONTRIBUTING.md:5`, `services/budget-api/src/lib/asyncHandler.ts:1`, `services/content-scheduler-api/src/workers/autoPostWorker.ts:47`). The surprising mismatch is that deployment-gate tests pass even though a deployment consumes an output the producer never exports (F1).

## Audit Report

Findings are grouped by dimension; High precedes Medium and Low. **Fact** denotes inspected source or executed evidence; **judgment** denotes impact/severity interpretation. No Critical issue was established in the inspected sample.

### DevEx, operations and testing

#### F1: Content Scheduler deployment condition references an unexported output — High ✅ [PR #841](https://github.com/Stoffer-Industries/sindustries/pull/841)

**Fact:** `.github/workflows/ci.yml:16` exports nine change outputs but omits `content_scheduler_api`. The filter exists at line 58, and the scheduler deployment requires `needs.changes.outputs.content_scheduler_api == 'true'` at line 1133. The independent output-reference check returned exactly `content_scheduler_api` as missing. The existing contract suite passed; its deployment loop checks merge-gate dependency and `always()` but not output production (`infra/cloud/scripts/tests/ci-deployment-gates.test.sh:113`).

**Consequence/judgment:** this automatic entry point cannot select scheduler API deployment, even for scheduler-only changes. The worker has its own exported output (`.github/workflows/ci.yml:20`), allowing API/worker revision divergence. Manual deployment paths may still work; no live outage is asserted.

**Classification:** `tracked-code-task`. ➡️ Tracked by task 1ecf5244 (`1ecf5244-9396-44e6-8f4b-79a87b0fc2c3`). Restore the export and test all consumed outputs, not just this one service. Deployment behavior changes are not garden-safe.

### Security

#### F2: Secret scanning remains advisory at the enforcement point — High

**Fact:** the gitleaks action has `continue-on-error: true` (`.github/workflows/ci.yml:964`). Its comment describes a license provisioning dependency (`.github/workflows/ci.yml:950`). Including the gitleaks job in merge-gate dependencies (`.github/workflows/ci.yml:1062`) does not turn the ignored step failure into a failing job.

**Consequence/judgment:** a positive scan or scanner execution failure need not prevent merging. Local hooks are useful but cannot establish server-side enforcement for every contributor. This finding does **not** claim a secret was found, nor that the live organization currently lacks a license.

**Classification:** `needs-human-decision`. Choose licensed-action provisioning or an approved CLI-based scanner, then implement a fail-closed gate with a synthetic-secret fixture. No duplicate implementation task is created before that operational/licensing decision.

Security strengths in the inspected sample include session-derived Budget ownership (`services/budget-api/src/routes/transactions.ts:50`), token encryption before repository writes (`services/budget-api/src/repos/akahuRepo.ts:9`), and method-scoped mutation authentication in Tasks (`services/tasks-api/src/app.ts:91`). Public reads are explicitly intentional in the inspected auth comments, not silently classified as an exploit; internet exposure and data-classification policy were not verified.

### Code quality and error contracts

#### F3: Malformed JSON is reported as an internal server error — Medium ✅ [PR #842](https://github.com/Stoffer-Industries/sindustries/pull/842)

**Fact:** Tasks parses JSON before routing (`services/tasks-api/src/app.ts:62`); its final error handler only preserves `entity.too.large`, then sends 500 for all other errors (`services/tasks-api/src/app.ts:122`). Budget follows the same pattern (`services/budget-api/src/app.ts:49`, `services/budget-api/src/app.ts:84`). Thus an Express JSON parser `entity.parse.failed` error reaches the generic 500 branch instead of retaining its client-error status.

**Consequence/judgment:** malformed client input inflates server-failure signals and can mislead clients into retrying an unrecoverable request. This is a source-proven branch mapping; no live malformed requests were sent during the audit.

**Classification:** `tracked-code-task`. ➡️ Tracked by task 90aea4c0 (`90aea4c0-37ce-4766-98f4-1fcf29b69bf1`). Introduce a narrow sanitized 400 mapping and regression tests, preserving 413 and genuine 500 responses. Observable status changes are not garden-safe.

### Architecture and performance

#### F4: Analytics reads materialize all matching events — Medium

**Fact:** task history uses an uncapped `findMany` and maps the complete result (`services/tasks-api/src/routes/featureTaskAnalytics.ts:225`). Weekly analytics constrains time, not event count, and loads matching events into memory (`services/tasks-api/src/routes/featureTaskAnalytics.ts:289`, `services/tasks-api/src/routes/featureTaskAnalytics.ts:308`). Percentile calculation also copies and sorts arrays (`services/tasks-api/src/routes/featureTaskAnalytics.ts:280`).

**Consequence/judgment:** request cost grows with event volume, including up to a year of events for weekly queries. Actual scale and latency are unknown; this is a scaling risk, not evidence of a current incident. Arbitrary truncation would corrupt statistics.

**Classification:** `tracked-research-task`. ➡️ Tracked by task c1f6fd7f (`c1f6fd7f-7fe4-4662-ab19-386444de7a5e`). Measure workload and consumers before selecting pagination, database aggregation or a cache. API semantics and percentile correctness exclude this from code garden. ✅ [PR #893](https://github.com/Stoffer-Industries/sindustries/pull/893)

Architecture otherwise shows appropriate domain separation in the inspected entry points; no service extraction or framework rewrite is justified by this sample (`services/tasks-api/src/app.ts:15`, `services/budget-api/src/app.ts:72`).

### Testing and type safety

#### F5: Backend TypeScript services have no compiler gate — Medium

**Fact:** Tasks, Budget and Content Scheduler scripts run through `tsx` and Vitest but define no `typecheck` script (`services/tasks-api/package.json:6`, `services/budget-api/package.json:6`, `services/content-scheduler-api/package.json:6`). CI explicitly typechecks Budget domain/mobile (`.github/workflows/ci.yml:535`) but has no corresponding non-emitting compiler step for those three API workspaces. Tasks and Budget configs also set `strict: false` (`services/tasks-api/tsconfig.json:6`, `services/budget-api/tsconfig.json:6`).

**Consequence/judgment:** successful transpilation and tests do not guarantee compiler-level consistency for unexercised service paths. Diagnostic counts were not measured, so immediate strict-mode enforcement is not recommended.

**Classification:** `tracked-research-task`. ➡️ Tracked by task fbe5aa19 (`fbe5aa19-aec0-47f3-8c5c-9fdeedccfc3c`). Baseline compiler diagnostics with generated Prisma clients before proposing a bounded gate. Broad type/import repairs are not assumed behavior-preserving.

### Documentation

#### F6: Contributor CI inventory omits the scheduler database distinction — Low ✅ [PR #840](https://github.com/Stoffer-Industries/sindustries/pull/840)

**Fact:** the inventory says only “content-scheduler-api vitest” (`CONTRIBUTING.md:106`), while CI defines a separate `content-scheduler-api-db-integration` job (`.github/workflows/ci.yml:379`) and requires it at line 1049.

**Consequence/judgment:** the list underspecifies which persistence checks contributors should reproduce locally; it does not prove missing tests. Clarify rather than replace the onboarding guide.

**Classification:** `garden-safe`. Documentation-only clarification, left to code garden; no separate task required.

### Dependencies and limitations

Nested lockfiles also exist, but their presence alone is not a defect. Registry advisory queries, full install reproducibility, transitive license review and runtime reachability were not executed; no CVE, unsupported-version or license-risk claim is made from version strings alone.

### Strengths and verification

- **Ownership checks and encrypted secrets:** Budget verifies transaction ownership and encrypts Akahu tokens on write (`services/budget-api/src/routes/transactions.ts:50`, `services/budget-api/src/repos/akahuRepo.ts:9`).
- **Guarded local environments:** Tasks rejects unexpected local API/database port pairing (`services/tasks-api/src/server.ts:21`).
- **Explicit asynchronous reconciliation:** auto-post checks removal, publication and stale schedule versions before dispatch (`services/content-scheduler-api/src/workers/autoPostWorker.ts:53`).
- **Multi-layer CI:** real database jobs and a single merge gate exist; preserve them while repairing F1 (`.github/workflows/ci.yml:379`, `.github/workflows/ci.yml:1037`).
- **Executed:** `node --test tests/cloud/tests/staging-workflows.test.mjs` passed 12/12; `bash infra/cloud/scripts/tests/ci-deployment-gates.test.sh` passed. These are local harness/static checks, not live staging validation.
- **Executed diagnostic:** extracted all `needs.changes.outputs.<name>` references and compared them with `jobs.changes.outputs`; the only missing producer was `content_scheduler_api`.
- **Not executed:** full unit/E2E/database matrix, deployment, production probing, full secret scan, compiler baseline, dependency audit and load testing. Findings above distinguish source inference from executed evidence.

## Improvement Strategy

| Theme | Target state and principle | Measurable completion |
| --- | --- | --- |
| Executable contracts | Validate links between CI producer, consumer and path filter, not merely job existence. | Zero undefined output references; scheduler-only and unrelated-path fixtures; missing-export mutation fails. |
| Honest failure boundaries | Separate client faults, service faults and security gate failures. | Malformed JSON 400, oversized body 413, internal fault 500 in both APIs; secret fixture blocks merge after F2 decision. |
| Evidence before scaling/refactoring | Establish service query and compiler budgets before selecting implementation. | Research records reproducible volume/latency/memory and per-service diagnostics with owners and follow-up scope. |
| Maintain the operational map | Keep contributor instructions aligned with executable checks. | Scheduler unit/DB jobs and reproduction commands are explicitly identified. |

Trade-offs: do not rewrite Express, merge service databases, turn on strict TypeScript everywhere, silently paginate analytics, or build a cache without workload evidence. Do not treat intended public reads as a vulnerability without a deployment/data-policy assessment. Do not run blanket dependency upgrades based on stale version intuition. Keep product functionality and data migrations outside code garden. F2 needs an owner decision, not a silent licensing or scanner-platform commitment.
