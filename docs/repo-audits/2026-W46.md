## Repo Map

### Purpose, stack, and flow

SIndustries combines personal/internal task delivery, budgeting, content publishing, fitness tracking, and a public company website. It is beyond prototype maturity, but staging topology and production rollout remain active engineering work (`README.md:5`, `README.md:27`).

| Area | Role and evidence |
| --- | --- |
| `apps/` | React/Vite Tasks, Mission Control, GymTrack, and website; Expo/React Native Budget mobile. Dependency/runtime declarations are in each app's `package.json`. |
| `services/tasks-api/` | Express/TypeScript task/workflow API; app mounts authentication then domain routers (`src/app.ts:78`). Bounded task queries use Prisma (`src/routes/tasks.ts:387`). |
| `services/budget-api/` | Express/TypeScript financial data API; session middleware gates domain routers (`src/app.ts:77`), with shared `packages/budget-domain/`. |
| `services/content-scheduler-api/` | Express/TypeScript publishing API and separate BullMQ worker; adapter choice precedes route construction (`src/app.ts:25`, `src/app.ts:65`). |
| `services/gymtrack-mcp/` | Node JavaScript MCP/OAuth service over Supabase; middleware and application wiring in `src/app.js:298`. |
| `packages/` | Design tokens/UI, Budget domain types, and Node OpenTelemetry, declared as npm workspaces (`package.json:20`). |
| `infra/cloud/` | Fly/Vercel deployment, health probes, and the new single-Machine staging supervisor/nginx router (`platform/platform-services.mjs:78`, `fly/platform.fly.toml:47`). |
| `agents/` | Skills/cron prompts, Python content workflows and Rust feature-task orchestration (`agents/workflows/feature-task/Cargo.toml:1`). |
| `docs/`, `tests/`, `scripts/` | Specs/system references, cloud verification, and enforced development/CI contracts (`CONTRIBUTING.md:110`, `docs/CONVENTIONS.md:9`). |

Typical flow: browser/mobile → service authentication/router → domain-owned Prisma schema; content mutations additionally schedule Redis/BullMQ work → publishing worker. Staging adds Fly → nginx host/prefix dispatch → three HTTP services, plus the queue worker on the same Machine (`infra/cloud/platform/nginx.conf:111`, `infra/cloud/platform/platform-services.mjs:78`). This is process consolidation, not a merger of data ownership.

Discovery sampled root/workspace manifests, lockfile metadata, TypeScript and Rust build configuration, CI jobs, Docker/Fly/nginx definitions, service entry/app/middleware/routes, and onboarding/conventions. Root `package-lock.json:3` uses lockfile version 3; platform installation uses frozen `npm ci` (`infra/cloud/docker/platform.Dockerfile:46`). Node 22 Alpine is the platform image target (`infra/cloud/docker/platform.Dockerfile:34`); service runtime scripts use `tsx`, not compiled production JavaScript. Existing conventions favor explicit service boundaries, injected dependencies, Vitest/real-Postgres suites, contract tests, and spec-first changes. The largest surprise is the gap between newly consolidated runtime behavior and tests predominantly validating process/config structure.

## Audit Report

Severity denotes consequence at the observed internal/staging maturity, not a claim of production exploitation. **Fact** means source or local execution verified; **judgment** identifies risk or recommended priority. Line references are relative to the audited commit, not later main.

### Architecture and operations

**F1: Spawn state is reported as platform readiness — High — tracked-research-task.** ➡️ Tracked by task `0a5a4bff` (`0a5a4bff-510e-4b46-b0b6-e2f8ab2bcb22`).

- **Fact:** `infra/cloud/platform/platform-supervisor.mjs:142` sets `state = 'running'` immediately after spawning; `:352` computes readiness exclusively from running states; `:369` turns that value into HTTP 200/503. Fly checks `/__status` (`infra/cloud/fly/platform.fly.toml:137`). Child commands include npm prestart work (`infra/cloud/platform/platform-services.mjs:82`).
- **Reproduction:** importing `createSupervisor` with injected EventEmitter children, no listeners and no service I/O produced `{"ready":true,"listenersStarted":0,"children":["running"]}`. This exercises the actual readiness calculation, not a live deployment.
- **Judgment/consequence:** startup work or a live-but-hung child can yield a green platform check while requests fail. Crash-loop detection is useful but does not prove readiness. Investigate HTTP/worker health signals and their failure thresholds before implementing shared-fate changes.

### Security and availability

**F3: Secret scanning is advisory at the merge gate — High — needs-human-decision.** ➡️ Tracked by task `2b3962b1` (`2b3962b1-7d8c-433e-beec-859de2f5b715`).

- **Fact:** `.github/workflows/ci.yml:1214` invokes gitleaks with `continue-on-error: true` at `:1215`; its job is a merge-gate dependency (`:1312`). The comment at `:1199` records an org-license prerequisite, not proof that a license currently exists.
- **Judgment/consequence:** findings or scanner setup failure can leave the dependency successful, so the merge gate does not enforce secret-scan success. No credential value was searched for publication or included in this report, and no actual leak is asserted.
- Decide whether to provision the action's license or use an approved license-independent CLI path. Until then, document the accepted enforcement gap; local hooks are not a server-side guarantee.
- **Resolution (task `2b3962b1`):** the licence-independent path was taken. The `gitleaks` job now runs the pinned gitleaks CLI (MIT, no organisation credential) through the shared entrypoint `infra/cloud/scripts/run-secret-scan.sh`, with `continue-on-error` removed, and a synthetic secret fails both the scan job and the merge gate. The licensing question in Q1 below is narrowed to "keep the CLI path, or migrate back to the licensed action if a licence is ever provisioned"; it no longer blocks enforcement.

**F2: Proxied API clients share the default rate-limit identity — Medium — tracked-research-task.** ➡️ Tracked by task `0a5a4bff` (`0a5a4bff-510e-4b46-b0b6-e2f8ab2bcb22`).

- **Fact:** nginx forwards requests to loopback upstreams and appends `X-Forwarded-For` (`infra/cloud/platform/nginx.conf:117`). Tasks, Budget and Scheduler app factories do not configure `trust proxy` (`services/tasks-api/src/app.ts:37`, `services/budget-api/src/app.ts:25`, `services/content-scheduler-api/src/app.ts:65`); their rate-limit factories use the library's default IP key (`services/tasks-api/src/middleware/rateLimit.ts:9` and counterpart files). A source search found the explicit setting only in MCP (`services/gymtrack-mcp/src/app.js:310`).
- **Judgment/consequence:** on this topology, the proxied APIs key on the nginx peer rather than distinct users, so one client can consume the quota for others at protected endpoints. This is a source-established configuration gap, not a measured live quota incident. The Fly/nginx hop chain and header-spoofing boundary must be verified; blindly copying MCP's one-hop setting or trusting all forwarded headers is not a safe fix.

**F6: Backend compiler debt is bounded, not eliminated — Low — needs-human-decision.**

These are committed allowances, not newly measured current compiler output. Tasks still has `strict: false` (`services/tasks-api/tsconfig.json:19`).
- **Judgment/consequence:** the ratchet prevents worsening but existing route/payload typing defects remain outside a clean compiler guarantee. Prioritize payload-boundary fixes if these modules change; do not suppress diagnostics or enable strict mode wholesale as cleanup.

### Performance

**F5: Scheduler list reads grow with retained publishing history — Medium — needs-human-decision.**

- **Fact:** `services/content-scheduler-api/src/routes/contentScheduler.ts:130` fetches all non-removed items (or all matching a status), ordered and including thread parts, with no `take` or cursor (`:137–149`). The route is deliberately publicly readable (`services/content-scheduler-api/src/app.ts:134`).
- **Judgment/consequence:** query materialization, response bytes, and client rendering grow with retained history. Actual row counts, latency and traffic were not measured; this is not evidence of current overload. Choose retention/history UX and a backward-compatible paging contract before changing the API. Tasks' bounded list implementation (`services/tasks-api/src/routes/tasks.ts:387`) is a useful local precedent, not a drop-in replacement.

## Improvement Strategy

1. **Make runtime claims observable (F1/F2).** Target readiness from bounded service/worker checks and client identity from a verified trusted hop chain. Done: a non-listening/hung child cannot satisfy readiness; two real proxy-path clients have independent quotas; spoofed headers cannot select arbitrary identities. Trade-off: retain shared-fate staging, avoid introducing a new distributed control plane.
2. **Turn available safety evidence into enforced evidence (F3/F4).** Target required offline checks and a scanner whose failure actually blocks merging. Done: intentional negative fixtures fail their required jobs; documented exceptions are limited to genuinely external prerequisites. Trade-off: do not provision paid licensing or widen credential access without owner choice.
3. **Budget growth and typing debt explicitly (F5/F6).** Target bounded list contracts and decreasing diagnostic baselines. Done: an agreed page/retention limit verified on representative history, and a chosen route slice reducing compiler debt without suppressions. Trade-off: no speculative broad rewrite or silent API response truncation.
4. **Keep the operational map aligned (F7).** Target one authoritative topology/runbook linked from onboarding. Done: README states one staging Machine and app-wide rollback; no duplicate deployment procedure.
