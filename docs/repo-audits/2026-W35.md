# Sindustries Repository Audit — 2026-W35

## Executive Summary

**Health grade: B–.** Two big structural moves landed this week — the Content
Scheduler backend was extracted into its own `services/content-scheduler-api`
(task `94d5e4fc`), and the first cloud-deploy slice shipped a Fly.io staging
pipeline for `tasks-api` (task `b2f62c36`, WS1 PR #1). Both are the right
direction, but both shipped with a concrete break that CI cannot see. **(1)** The
new `tasks-api` staging Docker build (`infra/cloud/docker/tasks-api.Dockerfile:38`)
runs `pnpm install --frozen-lockfile` against a root-only, stale `pnpm-lock.yaml`
that declares exactly one importer (`.`, jsdom) and contains zero of tasks-api's
runtime deps (express, @prisma/client, tsx, bullmq, ioredis) — yet the repo is
npm-managed everywhere else (CI runs `npm ci`; `package-lock.json` is 810 KB; the
gymtrack-mcp Dockerfile it claims to mirror uses `npm install`). `--frozen-lockfile`
against that lockfile cannot resolve the workspace, so the staging deploy build
fails; the two follow-up hotfix commits this week (`cf9ab77`, `e6e015f`) show the
deploy path is already being debugged reactively post-merge. **(2)** The Content
Scheduler extraction dropped the `requireAuthenticatedUser` mutation gate that
W34 verified as the W33 fix: in the new service, `createApp` mounts every write
route with no auth middleware (`services/content-scheduler-api/src/app.ts:108`),
so create/edit/approve/unapprove/remove/reorder are unauthenticated; only
`publish` (x-actor-secret) and `imports` (ingest-secret) are guarded, and the
auto-post worker reaches the real-X publish through `publishContentSchedulerItem`
with no secret at all — so unauthenticated `POST /items` → `POST /approve` can
schedule a real tweet the moment this HTTP app is exposed at its already-referenced
public URL (`sindustries-content-scheduler-api-staging.fly.dev`). **(3)** That new
3,416-LOC service has six test files and **zero** CI jobs — the third straight
week a new security-relevant subsystem shipped with tests that never run in CI
(W33 gymtrack-mcp, W34 cto-craft). Top risks: broken staging build, unauthenticated
scheduler writes on a to-be-public service, and the recurring untested-new-service
pattern. Top opportunities: delete the vestigial `pnpm-lock.yaml` and align the
Dockerfile to npm; carry the auth gate into the extracted service before HTTP
exposure; add a `content-scheduler-api` CI job. No exploited-in-production Critical
was verified; findings 1 and 2 are pre-deploy blockers.

## Repo Map

**Purpose:** Monorepo for Sindustries product surfaces and agent-operated
workflows: Tasks, Mission Control, GymTrack, Budget, Website, shared UI/design
tokens, backend APIs, and Rust/Python automation.

**Stack:** Node.js 22; **npm workspaces** (`apps/*`, `packages/*`, `services/*`);
React/Vite web apps; Expo mobile; Express + Prisma + PostgreSQL services
(`tasks-api`, `budget-api`, new `content-scheduler-api`); BullMQ + Redis for durable
auto-post; Supabase + a standalone OAuth MCP server (`gymtrack-mcp`); a Rust
feature-task workflow; Python/LangGraph operational workflows; GitHub Actions CI;
new Fly.io staging deploy for `tasks-api`.

**Architecture:** `apps/*` clients call domain services; `packages/*` holds shared
UI/tokens/telemetry/domain code; each domain owns its own service (the extraction
tech design's "no aggregate Mission Control backend" principle,
`docs/specs/content-scheduler-service-extraction-tech-design.md:22`);
`services/content-scheduler-api` now owns the scheduling queue, approval metadata,
publish guard, and X integration; `infra/cloud/*` owns the new Fly deploy topology.

**Key directories:** `apps/` user products; `services/` backend domains (now four:
budget-api, content-scheduler-api, gymtrack-mcp, tasks-api); `packages/` shared
libs; `agents/workflows/*` automation; `infra/cloud/` Fly/Docker deploy artefacts;
`.github/workflows/` CI/deploy; `docs/` architecture, specs, runbooks, audits.

**Surprise:** the repo carries **two lockfiles for one workspace** — an 810 KB
npm `package-lock.json` (authoritative; what CI installs from) and an 11 KB
`pnpm-lock.yaml` whose `importers:` section lists only the root package. The new
staging Dockerfile is the only consumer of the pnpm lockfile, and it can't build
against it.

## Audit Report

### Strengths

- **The extraction has clean seams.** `content-scheduler-api` keeps the guard, the
  X client call, and status/error persistence in one `publishContentSchedulerItem`
  service (`services/content-scheduler-api/src/routes/contentSchedulerPublishService.ts:1-11`)
  so manual and auto paths cannot drift, and the job scheduler is a provider-neutral
  adapter (`contentSchedulerJobs.ts`) with a real BullMQ implementation for
  durability. The module boundaries are good; the gap is auth, not structure.
- **gymtrack-mcp's RFC 7591 DCR is carefully validated.** `/oauth/register`
  (`services/gymtrack-mcp/src/app.js:347`) enforces redirect-URI rules (no
  wildcards/fragments/non-http schemes, a max count, https-only metadata URLs,
  length caps — `:76-140`), never echoes `client_secret` (`:201`), redacts Supabase
  URLs from error output (`:229`), and caps the JSON body at 100 KB (`:316`).
- **The deploy workflow is least-privilege and scoped.**
  `deploy-staging-tasks-api.yml` uses `permissions: contents: read`, references
  `FLY_API_TOKEN` by name only, path-filters to the relevant sources, and gates on
  a real `/health` smoke check with retries — a solid pipeline shape once the build
  itself works.
- **Auto-post durability is real.** The worker reconciles against current item
  state, defends against stale schedule versions and early fires, and is idempotent
  for the OK case to avoid duplicate tweets on queue retry
  (`services/content-scheduler-api/src/workers/autoPostWorker.ts:46-138`).

### Security & correctness

**[High] The tasks-api staging Docker build cannot resolve dependencies: it runs `pnpm install --frozen-lockfile` against a root-only, stale `pnpm-lock.yaml` while the repo is npm-managed.**

- **Where:** `infra/cloud/docker/tasks-api.Dockerfile:31-38` copies `pnpm-lock.yaml`
  and runs `RUN pnpm install --frozen-lockfile --filter @sindustries/tasks-api...`.
  The lockfile (`pnpm-lock.yaml:7-12`) declares a single importer — `.` with only
  `jsdom` — and its `packages:` section is entirely jsdom's transitive tree. It
  contains **zero** occurrences of `express`, `@prisma/client`, `tsx`, `bullmq`,
  `ioredis`, or `@sindustries/otel-node`, all of which are tasks-api runtime deps
  (`services/tasks-api/package.json` dependencies). Meanwhile every CI job installs
  with `npm ci` / `cache: npm` (`.github/workflows/ci.yml:24,28,...`),
  `package-lock.json` is the 810 KB authoritative lockfile, the root `package.json`
  has no `packageManager` field, and the gymtrack-mcp Dockerfile this one claims to
  "mirror" uses `npm install --omit=dev` (`services/gymtrack-mcp/Dockerfile:5`).
- **Why it matters:** `pnpm install --frozen-lockfile` fails by design when the
  lockfile is missing importers/deps for the manifests present, so the Fly build
  step in `deploy-staging-tasks-api.yml` fails before the app ever starts. The
  deploy triggers on push to `main` touching `services/tasks-api/**` or
  `infra/cloud/**` — which happened this week — and the two subsequent hotfix
  commits (`cf9ab77` align http_check, `e6e015f` drop a non-existent
  `pnpm-workspace.yaml` from the COPY) show the deploy is being fixed reactively
  post-merge rather than validated pre-merge. Nothing in CI builds the Docker image,
  so this is invisible until deploy.
- **Fact vs judgment:** *Fact* — the Dockerfile uses pnpm + frozen lockfile; the
  pnpm lockfile has one importer and none of tasks-api's deps; CI and the sibling
  Dockerfile use npm. *Judgment* — the build fails at `pnpm install`; severity High
  (staging-only, no user/production impact, but the just-shipped deploy path is
  non-functional).
- **Severity:** High. → Classification: `tracked-code-task` (align the Dockerfile to
  the repo's npm/`package-lock.json` toolchain and delete the vestigial
  `pnpm-lock.yaml`, or make pnpm the real workspace manager — one manager, one
  lockfile; see OQ1).

**[High] The Content Scheduler extraction dropped the `requireAuthenticatedUser` mutation gate: all CRUD/approve/remove/reorder write endpoints in the new service are unauthenticated, and the auto-post path reaches real-X publish with no secret.**

- **Where:** `services/content-scheduler-api/src/app.ts:63-119` builds the app with
  helmet, CORS, a rate-limit on only `.../items/:id/publish`, and mounts
  `contentSchedulerRouter`, `contentSchedulerAutoPostRouter`, and `xTweetRouter`
  under `/api/v1` — **with no auth middleware**. The write routes
  (`contentScheduler.ts:151` create, `:239` edit, `:351` approve, `:405` unapprove,
  `:524` posted-url, `:566` remove, `:614` reorder) have no per-route auth check;
  only `publish` (`:459-472`, `x-actor-secret` when `X_ACTOR_SECRET` set) and
  `imports/cto-craft` (`:723-735`, `x-content-ingest-secret`) are guarded. The
  `actor()` helper still reads `req.user?.actor` and its comment cites the
  `requireAuthenticatedUser` middleware "(task 0719a8e3)" (`:58-64`), but that
  middleware was left behind in `tasks-api` (`services/tasks-api/src/middleware/requireAuth.ts`
  still exists; the new service has no `middleware/requireAuth.ts`) — so `req.user`
  is always undefined and `actor()` degrades to the `x-actor` header or `'unknown'`.
- **Why it matters:** The auto-post worker publishes via
  `publishContentSchedulerItem(item.id, 'auto')`
  (`workers/autoPostWorker.ts:106`), and `x-actor-secret` is checked only in the
  HTTP `publish` route handler, not in the shared publish service — so the chain
  *unauthenticated `POST /items` (body + near-future `scheduledFor`) → unauthenticated
  `POST /items/:id/approve` (`:351`, enqueues auto-post) → worker fires →
  `publishContentSchedulerItem` → real X client (when creds set)* posts a tweet from
  the company account with no secret anywhere in the path. The deploy topology
  already references this service at a public host: tasks-api's staging env sets
  `CONTENT_SCHEDULER_API_BASE_URL=https://sindustries-content-scheduler-api-staging.fly.dev/api/v1`
  (`infra/cloud/README.md:58`). In `tasks-api` (pre-extraction, W34) these same
  routes were gated by `app.use('/api/v1/content-scheduler', gateMutations)`; the
  extraction silently removed that protection.
- **Fact vs judgment:** *Fact* — no auth middleware is mounted in the new service;
  only publish/imports have secret checks; the auto path bypasses the publish
  route's secret; the public base URL is already wired. *Judgment* — this is a
  security regression and a pre-HTTP-exposure blocker; severity assumes the
  content-scheduler-api HTTP app is (or will be) exposed at the referenced URL. If
  it is genuinely never HTTP-exposed (worker-only), downgrade to Medium (see OQ2).
- **Severity:** High. → Classification: `tracked-code-task` (re-mount an auth gate —
  a session/Bearer or actor-secret requirement — on all write routes before HTTP
  exposure; small tech design recommended, OQ2).

**[Low] gymtrack-mcp's open `/oauth/register` endpoint has no rate limiting.**

- **Where:** `services/gymtrack-mcp/src/app.js:347` exposes unauthenticated RFC 7591
  Dynamic Client Registration. There is no `express-rate-limit` (absent from
  `services/gymtrack-mcp/package.json`) and no limiter/throttle in `app.js`; the only
  bound is the 100 KB body cap.
- **Why it matters:** Open, unauthenticated, unthrottled client registration on an
  internet-facing service (`gymtrack-deploy.yml` deploys it) lets an attacker create
  unbounded `oauth_clients` rows — a cheap DB-bloat / registration-spam availability
  nuisance. RFC 7591 permits open registration but pairs it with throttling or
  software statements in practice.
- **Fact vs judgment:** *Fact* — no rate limiting on the registration path.
  *Judgment* — low real-world impact (bloat, not compromise); validation is
  otherwise strong.
- **Severity:** Low. → Classification: `tracked-code-task` (add a rate limit to the
  registration/authorize endpoints).

### Testing

**[Medium] The new `content-scheduler-api` service (3,416 LOC, six test files) has no CI job — the third consecutive week a new security-relevant subsystem shipped with tests that never run in CI.**

- **Where:** `.github/workflows/*.yml` contains **zero** references to
  `content-scheduler-api` (grep across all five workflow files returns 0). CI has
  per-workspace jobs for tasks-api, budget-api, mission-control, otel-node, ash,
  feature-task (Rust), and the Python workflows (`ci.yml`), but none for the
  extracted service, whose suite (`test/contentScheduler.test.ts`,
  `contentSchedulerAutoPost.test.ts`, `contentSchedulerAutoPostDurable.test.ts`,
  `contentSchedulerImport.test.ts`, `contentSchedulerItems.test.ts`,
  `xTweet.test.ts`) runs under **vitest** (`package.json` `"test": "vitest run"`),
  a runner no existing CI job invokes.
- **Why it matters:** The auth regression above, the auto-post durability path, and
  the import contract all live in code CI never exercises, so regressions ship
  undetected. This directly recurs the W33 (gymtrack-mcp) and W34 (cto-craft)
  theme: a new security-sensitive subsystem shipped with tests that don't run in CI.
- **Severity:** Medium. → Classification: `garden-safe` / quick win — add a
  `content-scheduler-api` job mirroring the existing service jobs (Postgres service
  container + Prisma generate/migrate + `npm test --workspace @sindustries/content-scheduler-api`),
  ensuring the vitest runner is actually invoked.

### Dimensions rated healthy (one line each)

- **Architecture & design:** the domain-per-service split and the single-publish-path
  design are sound; the only architectural debt is the two-lockfile ambiguity.
- **Performance:** no new N+1 or unbounded-growth patterns in the reviewed paths; the
  worker is bounded and idempotent, and the import posts a single bounded batch.
- **Dependencies:** service manifests pin bounded ranges; the concern is lockfile
  *hygiene* (dual npm/pnpm lockfiles), not heavy or unmaintained packages.
- **Documentation:** the extraction tech design, cloud README, and deploy workflow
  comments are accurate and specific; the one stale contract is `actor()`'s comment
  referencing a middleware the extracted service no longer has (see High finding).

## Improvement Strategy

**Themes explaining most findings:**

1. **New deploy/extraction artefacts don't match the repo's actual toolchain.** The
   staging Dockerfile adopted pnpm against a vestigial lockfile in an npm-managed
   repo; the extracted service adopted vitest and lost its auth middleware. *Target
   state:* new artefacts inherit the established toolchain (one package manager, one
   lockfile) and the established cross-cutting guarantees (auth gate, CI job) rather
   than re-deriving them partially. *Principle:* an extraction/deploy is a move, not
   a rewrite — carry the invariants with the code.
2. **Security-critical new code is under-covered by CI (recurring, 3rd week).**
   content-scheduler-api has no CI job, exactly as gymtrack-mcp (W33) and cto-craft
   (W34) didn't. *Target state:* every workspace/service with a suite has a CI job
   that runs it in its native runner. *Principle:* untested safety code is unshipped
   safety.
3. **The build/deploy path is validated post-merge, not pre-merge.** No CI job builds
   the Docker image or the deploy config, so Dockerfile breaks surface only on
   push-to-main (hence this week's reactive hotfixes). *Target state:* a PR-time
   docker-build (or `flyctl config validate` + image build) job for changed deploy
   artefacts. *Principle:* if it ships on merge, it should be proven before merge.

**Explicit non-goals (recommend NOT fixing now):**

- Don't migrate the whole monorepo to pnpm to "fix" the lockfile — the repo is
  npm-managed and CI proves it; the cheap correct fix is to delete `pnpm-lock.yaml`
  and use npm in the Dockerfile (unless there's a deliberate pnpm decision — OQ1).
- Don't build a full auth framework for content-scheduler-api now — re-mount the
  same gate `tasks-api` already uses; a bespoke scheme is scope creep.

**"Done" signals:** the tasks-api staging image builds and `/health` smoke passes; a
content-scheduler-api write request with no credentials is rejected; CI runs the
content-scheduler-api suite on changes to that path; a PR-time job builds the deploy
image.
